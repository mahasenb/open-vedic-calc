# CLAUDE.md — open-vedic-calc

This repo is a generic, standalone Vedic (BPHS) astronomical calculation service, licensed AGPL-3.0-only. It is reached only over HTTP by a bearer-token-holding caller. Rules below supplement the workspace CLAUDE.md; they do not replace it. That parent file is inherited here automatically, but **the skills it names are not** — only `CLAUDE.md` traverses upward. When a skill the parent names is absent from your session's skill list, the parent states where to Read it; an unresolved skill is a file to open, never a rule to skip.

## Product neutrality — absolute

This is a public AGPL repo. It must **never** name, hint at, or link the proprietary consumer that calls it — not in code, comments, docstrings, tests, commit messages, PR titles/bodies, issues, or docs. Refer to callers only in generic, role-based terms: "the caller", "the HTTP client", "the consumer". "The downstream backend" is acceptable only as a role description, never paired with a name.

The CI gate `ci/check_no_proprietary_refs.py` (run by `.github/workflows/ci.yml` on every change, including docs) is the enforcement mechanism. `_FORBIDDEN` is a **list** of compiled patterns: a legacy base pattern (the standalone word this file's own guard describes, excluding the Swiss Ephemeris URL and the astronomy/astronomical domain words) plus zero or more additional brand tokens read at runtime from the `PROPRIETARY_REF_TOKENS` env var (comma-separated), which CI populates from a GitHub Actions secret of the same name (`.github/workflows/ci.yml`, `boundary` job `env:` block). Standing rule: keep the secret's token list current as the consumer's branding evolves — a token set that only guards a superseded name silently permits a leak; updating it when you learn the brand or infra identifiers have changed is required work, not optional (an **owner** action: only the repo secret's value changes, never this file).

Critical subtlety: do **not** write the literal brand token into this CLAUDE.md, into the gate file's plaintext, into its tests, or into any other tracked file — the file is public, and the token itself would leak the association. The forbidden-term list beyond the legacy base pattern must be maintained out-of-band, exclusively via the `PROPRIETARY_REF_TOKENS` secret injected at CI time — never as public plaintext. If asked to "add the brand to the gate," the correct implementation is adding/rotating that secret's value, not editing source. When the env var is unset (e.g. a fork or external PR without secret access), the gate falls back to legacy-only matching and does not fail — absent optional config is not itself a leak.

The gate scans the full pushed commit range, not just the latest commit: `ci.yml` passes `${{ github.event.before }}..${{ github.sha }}` as the gate's commit-range argument, so a leak buried in an intermediate commit of a multi-commit push cannot slip through. The gate falls back to scanning just HEAD's message when the range is absent or contains git's zero-SHA "first push" sentinel.

Before every push, run the gate locally: `python ci/check_no_proprietary_refs.py`. Its behaviour (list-of-patterns, env-var token injection, commit-range scanning, fail-safe fallbacks) is covered by `ci/tests/test_check_no_proprietary_refs.py`. That file lives outside the `tests/` tree by design and is **not** swept by `pytest tests/`; `test.yml` and `publish.yml` each run it as its own explicit CI step (`pytest ci/tests/ -q`), separate from the main suite, so a future edit that regresses `_FORBIDDEN` back to a single regex or drops the env-token loop cannot pass CI green. `ci/tests/test_ci_runs_gate_regression_suite.py` is the regression guard on that wiring itself — it asserts some workflow step actually invokes `ci/tests/`. Extend both test files, never weaken them, and never put a real or synthetic-looking-real brand literal in the gate's test file either (it uses only an obviously-fake synthetic token, injected via the same env var).

## Engine conventions (astronomical correctness)

- Ayanamsa is LAHIRI. The ephemeris path and sidereal/ayanamsa mode are **THREAD-local** state (pyswisseph >= 2.10's thread-local `swed` struct), **not process-global** — every thread must apply both itself before it calls into `swe.*`/`drik.*`, or it silently computes on the Moshier fallback with the default Fagan/Bradley ayanamsa (~0.88 deg / 53 arcmin off Lahiri) instead of raising. `bphs_core/utils.py`'s `_ensure_thread_ephemeris_state()` applies `swe.set_ephe_path(...)` and `drik.set_ayanamsa_mode('LAHIRI')` once per thread, idempotently; `serialized_ephemeris` calls it on every invocation of every C-library entry point, so a new compute path gets it by construction as long as it carries that decorator — never assume a clean default on a thread that isn't provably decorated. `Chart._compute` additionally re-asserts `drik.set_ayanamsa_mode('LAHIRI')` inline (chart.py:178) on top of the decorator's guarantee; keep that re-assertion pattern in any new compute path as defense-in-depth — but the decorator, not the inline re-assertion, is what makes a new thread correct.
- **Ephemeris lock (thread-safety):** the underlying Swiss Ephemeris C library is not documented as safe for concurrent `swe_calc`/`swe_houses` calls from multiple threads — even once each thread's own path/ayanamsa state (above) is correctly configured — and Starlette's request pool + the scan-job pool in `app/jobs.py` both enter it concurrently. Every **new** runtime compute path that calls `swe.*`/`drik.*`/`charts.*` **must** be wrapped in `@utils.serialized_ephemeris` (bphs_core/utils.py) so it (a) gets the per-thread state above applied on every call, and (b) holds the process-wide `EPHEMERIS_LOCK` — and it must be decorated at **inner, millisecond-bounded granularity** (one chart, one day, one instant, one JD conversion), **never around a whole scan**: a whole-scan hold blocks every interactive route and the async submit path for the scan's remaining duration, reversing the "submissions never wait on scan compute" property below. The lock is an RLock, so nested decorated entry points are safe. Add each new entry point to the coverage list in `tests/test_ephemeris_lock.py::test_every_c_library_entry_point_is_serialized` — the test pins only the known set; this rule is the guard for future paths.
- Julian Day discipline (the rule that prevents the tz double-subtraction bug): pyjhora chart/drik functions (`charts.rasi_chart`, `drik.ascendant`, `drik.dhasavarga`, `drik.planets_in_retrograde`) expect a **local-clock JD** and subtract the place timezone themselves internally. Build the local JD and pass it **unmodified** to pyjhora — never pre-subtract the timezone (`_jd_from_person`, chart.py:80-91). Any swisseph call that needs true UT derives it separately as `jd_utc = jd - tz_offset_hours / 24.0` **at the call site** (chart.py:178). Never feed a tz-pre-subtracted JD to pyjhora, and never feed a local JD to a swisseph UT function — the two transports are distinct and are not interchangeable.
- The lagna/ascendant is computed **directly** from swisseph — `swe.houses(jd_utc, lat, lon, b"P")` → `ascmc[0]`, then sidereal-corrected as `(ascmc[0] - ayanamsa) % 360` (chart.py:194-203). **Never** take the ascendant from pyjhora's `rasi_chart()[0]`: it double-applies the timezone and lands the lagna tz-hours off. Fallback: if placidus (`b"P"`) raises (extreme latitudes), fall back to equatorial (`b"E"`) and record `house_system` accordingly (chart.py:192-201) — never silently return a placidus-labelled chart from an equatorial computation.
- Whole-sign is the primary house frame for planetary house assignment; Bhava-Chalit cusps are provided separately as sidereal Placidus cusps (chart.py:217-218, field `chalit_cusps`). Do not conflate the two — whole-sign house is the interpretive default, chalit is supplementary.
- **Lunar node model: the TRUE (osculating) node — owner-ruled 2026-08-17 — DECLARED in `bphs_core/utils.py` (`LUNAR_NODE_MODEL`) and never inherited.** Rahu is the true node; Ketu is exactly Rahu + 180°. This is a decision, not a default that happened to be in force. The engine already served the true node when the owner ruled it, so the ruling records authority and changes no served longitude. Measured over the supported birth-date span (1800-01-01..2400-12-31, `app/schemas.py`) at one-day steps against the real Swiss data files, the two models differ by up to **1.981465100° = 7133.2744 arcsec** (worst instant 1905-10-10 22:00 UT, refined at one-hour steps), and across those 219511 sampled days they place Rahu in a **different nakshatra pada on 28.85%** of them, a different nakshatra on 7.19% and a different rasi on 3.20%. That is more than twice the ~0.88° ayanamsa error above — an undeclared model was a ~2° accuracy exposure sitting behind a dependency resolve. Rationale for TRUE: every other graha here is a true/apparent modern-ephemeris position, so serving a smoothed mean element for one graha alone would make a single chart internally inconsistent. Second-order consequence worth knowing: the mean node is analytical and ephemeris-source-independent (measured max Swiss-vs-Moshier **0.000000295°**) while the true node carries the full ephemeris-source error (measured max **0.018175452° = 65.4316 arcsec**, at 1936-10-30), so this choice also decides whether an ephemeris-source defect can touch Rahu/Ketu at all.
- **The node model has three independent levers, and the obvious one is not the one that serves.** Measured, not read from documentation: set `jhora.const._RAHU` / `_use_true_nodes_for_rahu_ketu` to the mean node, compute a `Chart`, and it returns the true node anyway — unchanged to the last digit. The chart path is `charts.rasi_chart` → `drik.dhasavarga(jd, place, 1)`, and `dhasavarga` declares `set_rahu_ketu_as_true_nodes=True` as a **literal** parameter default (not `None`), so it rebuilds the body table from that literal and never consults the constants. `utils.apply_lunar_node_model()` therefore pins (1) the constants through `const.set_node_mode` — never by assigning `_RAHU` directly, which would desynchronise it from the boolean that `set_planet_list` reads — and (2) the mutable `drik.planet_list` global, and **verifies** (3) `dhasavarga`'s serving literal, which this repo cannot set. Any lever disagreeing with the declaration is a **hard failure at import**, never a warning; `bphs_core/__init__.py` imports `utils` first so the pin lands before any sibling module uses drik. Because lever 3 is a library literal, declaring `LUNAR_NODE_MODEL = "mean"` deliberately hard-fails instead of serving true-node charts under a mean-node banner: switching model means routing the chart path through `drik.dhasavarga(..., set_rahu_ketu_as_true_nodes=False)` and re-recording the Swiss goldens, and a one-word edit must not be able to look like that work was done. `pyjhora` is pinned to an exact version (`==4.8.6` in `pyproject.toml`, matching `uv.lock`) for the same reason `pyswisseph` is — every one of those three levers lives inside it. Contract: `tests/test_lunar_node_model.py`; extend it, never weaken it.
- **Shadow-graha retrogression: DECLARED in `bphs_core/utils.py` (`PERPETUALLY_RETROGRADE_GRAHAS = {"Rahu", "Ketu"}`) and never inherited.** BPHS reads both lunar nodes as permanently retrograde (vakri), and this engine serves them that way as a stated decision. What it served before the declaration existed was the **exact inverse**, on every chart: retrogression reaches a chart through `drik.planets_in_retrograde`, and that function drops both nodes from its loop unconditionally (`_planet_list = {p: p_id for p, p_id in planet_list.items() if p not in [const._RAHU, const._KETU]}`), so it can never name them and `chart.py`'s `pid in retro_planets` was `False` for Rahu and Ketu on every date. Measured 2026-08-07 on the frozen resolve over 1461 charts (2000-01-01..2019-12-27, 5-day steps): both shadow grahas retrograde on **0**, while the same sweep saw Saturn retrograde on 35.93% and Mercury on 19.16% — the sweep could observe retrogression and simply never saw it here. **Structural, not a sampling or ephemeris-runtime artefact**: identical under the real Swiss data files and the Moshier fallback. Why declared rather than derived from the ephemeris — under the declared TRUE (osculating) node the speed sign is *not* constant: over 350400 hourly Swiss samples (1990-01-01..+40y) the true node's longitude speed is **positive (direct) on 25.82%** of them, peaking **+0.128202129°/day at 2029-06-21 00:00 UT**, while the mean node is retrograde on 100% of the same span — so deriving the flag would report Rahu direct on roughly a quarter of charts, and the classical reading is a deliberate override of that signal, not a restatement of it. Near the turning points that sign is also ephemeris-source-dependent (**the same 2029-06-21 instant reads −0.001408427°/day under Moshier** — opposite sign), so a derived flag would not even be stable across the two runtimes this repo supports; keep any assertion on it out of `tests/` and inside the Swiss-only job. Applied by graha **name** through `utils.graha_is_retrograde(name, computed=…)` at **both** `chart.py` construction sites (the rasi loop and `_build_varga_chart`) — pinning one reads exactly like pinning both — and a declared name absent from `utils.PLANETS` **hard-fails at import** rather than silently matching nothing and handing the nodes back to the library. Blast radius, measured across four charts (including ones with retrograde classical grahas): **22 leaves move and all 22 are `is_retrograde` on Rahu/Ketu across the rasi chart and the ten vargas — Shadbala, Bhavabala, Ashtakavarga, Vimshopaka and combustion are byte-identical.** `_cheshta_bala` is the one strength limb that reads the flag, and it is only ever reached for the seven grahas in `SHADBALA_MINIMUMS` plus house lords from `get_sign_lord`, none of which is a node; `_apply_combustion` skips any graha absent from `_COMBUSTION_ORB`, which excludes both. Contract: `tests/test_shadow_graha_retrogression.py`; extend it, never weaken it.
- **Classical-graha retrogression in the divisional charts: PROPAGATED from one computation, and now observed.** Retrogression is a property of the INSTANT, not of a divisional mapping — a varga re-maps longitude onto a finer grid and cannot change the direction a graha is moving — so the flag every varga serves must equal the rasi flag for every graha. Structurally it already does: `_compute` calls `drik.planets_in_retrograde` **once** and hands the same result to all ten `_build_varga_chart` calls, so there is exactly one link where it can be severed, and measured across eight charts × eleven charts × seven classical grahas there were zero varga/rasi disagreements. What was missing was anything that would notice. Measured 2026-08-09 on the frozen resolve against the real Swiss data files: replacing `_build_varga_chart`'s `computed=pid in retro_planets` with `computed=False` — reporting every classical graha DIRECT in all ten vargas on every date — left the entire suite green at **741 passed, 0 failed**, and so did the inverse (`computed=True`, blanket vakri), and so did severing D9 alone, and so did dropping the flag in `app/main.py`'s `_pd_to_schema`. The shadow grahas were pinned in every varga, but `graha_is_retrograde` returns True for Rahu and Ketu whatever `computed` says, so those assertions are blind to precisely this mutation. Verified identical under **both** ephemeris runtimes. The two lunar nodes are deliberately **not** re-derived there — that file builds its expectations from `PERPETUALLY_RETROGRADE_GRAHAS`, and `tests/test_shadow_graha_retrogression.py` remains the tripwire on the declaration itself (measured: shrinking the declaration reddens that file and leaves this one green, which is the intended division). Extend it, never weaken it.
- **Position-flag word: DECLARED in `bphs_core/utils.py` (`POSITION_FLAGS = 66386`) and never inherited.** The third argument to `swe.calc_ut` decides the reference frame every served longitude is expressed in, and it used to come from `drik.PLANET_FLAGS`, which pyjhora builds at *its* import time from five `jhora.const.PLANET_POSITIONS_*` globals. Measured 2026-07-31, this repository unchanged, on two resolves: **pyjhora 4.8.6 → 66386, pyjhora 4.8.7 → 65810**, a difference of **576 = `FLG_NOGDEFL` (512) | `FLG_NONUT` (64)** — 4.8.7 flipped `PLANET_POSITIONS_USE_DEFLECTION` and `PLANET_POSITIONS_USE_NUTATION` from `False` to `True`. The declared word is `FLG_SWIEPH|FLG_SIDEREAL|FLG_TRUEPOS|FLG_NONUT|FLG_NOGDEFL|FLG_SPEED`; `FLG_TOPOCTR` is deliberately not taken (this service receives no observer altitude). **The three flags are coupled and only one of them currently moves a number.** Measured with the frozen resolve against the real Swiss data files over the supported span (1800-01-01..2400-12-31) at one-day steps, 219511 days × 9 grahas: dropping `FLG_TRUEPOS` (geometric → apparent) moves positions by up to **0.016817256° = 60.5421 arcsec** (Mercury, 2353-06-16 00:00 UT; Venus 44.7711″, Mars 38.9693″, Jupiter 30.0595″, Saturn 27.2519″, Sun 20.8489″, Moon 0.7632″, Rahu/Ketu 0.0146″), while dropping `FLG_NOGDEFL`+`FLG_NONUT` moves **0.000000000° on every graha on all 219511 days** — because under `FLG_TRUEPOS` swisseph ignores deflection and aberration outright, and for a sidereal request it applies `FLG_NONUT` unasked (retflag 65602 for a plain `FLG_SWIEPH|FLG_SIDEREAL` request). So the library's word moved and **no golden here could have caught it**: the served numbers were bit-identical. That inertness is conditional — clear `FLG_TRUEPOS` and `FLG_NOGDEFL` becomes worth 0.0711″ and `FLG_NOABERR` 20.8557″. Never reason about one of these flags without the others.
- **The position-flag word has three levers, and the serving one is a mutable global built before this package runs.** (1) `jhora.const.PLANET_POSITIONS_*`, read by `jhora.utils.set_flags_for_planet_positions()` on every call — the inherited default, and what moved between 4.8.6 and 4.8.7; (2) `drik.PLANET_FLAGS`, built from (1) at drik's import time and read at call time by `drik.sidereal_longitude`, `drik.dhasavarga` (hence `charts.rasi_chart`) and `drik.planets_in_retrograde` — this is what actually serves; (3) `jhora.const._TROPICAL_MODE`, which makes `drik.sidereal_longitude` ignore `PLANET_FLAGS` entirely and compute with `FLG_SWIEPH + FLG_SPEED` (tropical, ~24° away) — a pinned word that is bypassed is not a pin. `utils.apply_position_flags()` **compares (1) against the declaration and hard-fails at import on any disagreement**, then pins (2) and reads it back, then verifies (3). The comparison against (1) is the whole point: pinning alone would silently absorb a dependency that changed its mind, which is the exact failure the 576 move demonstrates. Scope, stated so it is not discovered later: this is the **planetary position** word only — the ascendant and Bhava-Chalit cusps come from `swe.houses(jd_utc, lat, lon, b"P")` (chart.py), which takes no flag word, and sunrise/sunset use pyjhora's separate `drik.RISE_FLAGS`/`SET_FLAGS` (measured **897 / 898, identical in 4.8.6 and 4.8.7**, so unmoved — and now declared in their own right, see the next bullet). Contract: `tests/test_position_flags.py`; extend it, never weaken it.
- **Sunrise/sunset convention word: DECLARED in `bphs_core/utils.py` (`RISE_FLAGS = 897`, `SET_FLAGS = 898`) and never inherited.** Every panchanga/electional limb is anchored to the day boundary — `drik.sunrise`/`sunset`/`moonrise`/`moonset`, and through them tithi, nakshatra, yoga, karana, the thirty muhurtas and the whole muhurat/lagna-shuddhi scan. Each of those calls `swe.rise_trans(..., rsmi=<word>, flags=PLANET_FLAGS)`, where the **`rsmi` word is DISTINCT from the ephemeris `flags` word `POSITION_FLAGS` pins** and decides *what counts as sunrise*: disc centre vs lower limb, true (geometric) vs apparent (refracted) horizon, rise vs set. The declared convention is swisseph's `BIT_HINDU_RISING` (896) — the Sun's disc **centre** at the **true, unrefracted** horizon (geocentric, no ecliptic-latitude correction), i.e. the classical *madhya-bimba* Hindu sunrise, matching `drik.sunrise`'s docstring and drik's own "geometric, true sunrise/set, refraction not considered" comment. This geometric disc-centre (Surya-Siddhanta) convention is **owner-ruled 2026-08-17**; the civil/almanac upper-limb-at-refracted-horizon convention is a real alternative a secular ephemeris reports, but the choice between them is settled, not an open question. It is load-bearing: **measured at Colombo 2024-03-20, clearing `BIT_NO_REFRACTION` moves sunrise 147.99 s (06:18:01 → 06:15:33)**, so the convention affects every limb measured from the day boundary. **Two levers, not three** — there is no runtime bypass here analogous to `_TROPICAL_MODE`: (1) `jhora.const.RISE_SET_HINDU_RISING`/`_USE_REFRACTION`/`_USE_DISC_CENTER_FOR_RISING`, the three globals `jhora.utils.set_flags_for_rise_set()` reads (the inherited default; flipping each moves the word to 769/770, 385/386, 9089/9090 respectively); (2) `drik.RISE_FLAGS`/`SET_FLAGS`, the mutable serving globals built from (1) at drik's import time. `utils.apply_rise_set_flags()` **compares (1) against the declaration and hard-fails at import on any disagreement** — the dependency-bump tripwire, exactly as `apply_position_flags` does — then pins (2) and reads both back. Pinning is behavior-preserving on the frozen resolve (the library already builds 897/898); the declaration is what makes a future `RISE_SET_*` default-flip legible instead of a silent day-boundary shift no electional golden could see. Contract: `tests/test_rise_set_flags.py`; extend it, never weaken it.
- **Two planet-id spaces exist and they are NOT interchangeable — graha names cross module edges, never raw integer body ids.** pyjhora numbers the grahas by the order of `utils.PLANETS` (Sun 0, Moon 1, **Mars 2, Mercury 3, Jupiter 4, Venus 5**, Saturn 6, Rahu 7, Ketu 8) — the space its chart *outputs* use (`charts.rasi_chart`, `drik.dhasavarga`, `drik.planets_in_retrograde` return these ids). swisseph numbers bodies Sun 0, Moon 1, **Mercury 2, Venus 3, Mars 4, Jupiter 5**, Saturn 6, Uranus 7, Neptune 8, node 10/11 — the space `swe.calc_ut` and `drik.sidereal_longitude` *consume* (pyjhora's own docstring: "The sequence number of 0 to 8 for planets is not followed by swiss ephemeris"). Sun, Moon and Saturn coincide, which is what lets a conflation survive spot checks: pass a PLANETS index to `sidereal_longitude` and a third of the output is right while Mars silently computes **Mercury**, Mercury→Venus, Jupiter→Mars, Venus→Jupiter, Rahu→**Uranus** and Ketu→**Neptune** — wrong celestial bodies, not small errors (measured 2026-07-31: index 7 returned 40.7495° = Uranus where the true node stood at 305.5916°). This shipped twice, in the transit endpoint's planet table and in the electional scorer's lord/malefic ids. The standing rule: per-body positions are requested **by graha name** through `utils.graha_sidereal_longitude(jd_utc, name)` — the single sanctioned boundary, which resolves names against explicit `swe.*` constants (Rahu = the declared `LUNAR_NODE_BODY`, Ketu = Rahu + 180°) — and `drik.sidereal_longitude` / `swe.calc_ut` are called **nowhere outside `bphs_core/utils.py`**. Never rebuild an id table from `enumerate(utils.PLANETS)`. A compute failure inside the lord/malefic scoring limbs **propagates** — it is never swallowed into a neutral-looking score (a swallowed `except: pass` there once reported wrong astrology as fine). Contract: `tests/test_graha_body_ids.py` — per-graha positive assertions against independent computations, plus an AST scan (parses code, cannot be defeated by comments/strings) that fails any new `sidereal_longitude`/`calc_ut` call site outside the boundary. Extend it, never weaken it.
- **Served clock times use ONE minute-rendering convention — TRUNCATE to the minute the instant falls in — via `bphs_core/muhurat.py::float_hours_to_hhmm`, byte-identical to pyjhora's `utils.to_dms(...)[:5]`.** Every HH:MM a muhurat/panchanga day serves — sunrise, sunset, moonrise, moonset, the 30 muhurtas, the auspicious/inauspicious/chogadiya/rahu-kala windows, and the tithi/nakshatra/yoga/karana end-times — must render on the same clock, because a period BOUNDARY is frequently the SAME instant as an event it is derived from: the night-muhurta division opens at exactly `drik.sunset(...)[0]`, and the chogadiya day/night split and one weekday's rahu-kala edge land on sunset too. `float_hours_to_hhmm` used to ROUND to the nearest minute while pyjhora's own `to_dms` (which formats every drik-computed time string this service then slices `[:5]`) TRUNCATES, so an 18:17:58 sunset served as `sunset` "18:17" but opened its night muhurta at "18:18" — register #176. The fix renders the helper on the library-native truncation (round the residual to whole seconds, then truncate the minute — exactly `to_dms`), and routes sunrise/sunset/moonrise/moonset through it on the float `[0]` so the event and the boundary derived from it pass through one formatter and cannot disagree. The BPHS-accurate value is the underlying float and is untouched by the choice; only the minute LABEL is pinned, and it is pinned to the convention already governing the 10 drik-string categories rather than introducing a second one. Convention chosen over nearest-minute rounding deliberately: rounding would (a) diverge from those 10 library-native categories, re-creating the same disagreement at the chogadiya/rahu-kala boundaries that also coincide with sunset, and (b) shift the minute-rendered sunrise the hora-lord limb consumes, drifting a computation this display fix must not touch. Contract: `tests/test_muhurat_deep.py::TestSingleClockConvention` locks `float_hours_to_hhmm ≡ to_dms(...)[:5]` (so the `[:5]` sites this helper does not itself format can never drift from it) and the served field==boundary invariant across a spread including the half-minute-second band where truncate and round diverge. Never reintroduce a second rounding convention for a served time.

## Determinism

This is an electional/astronomical engine — outputs must be reproducible.

- Astronomical outputs are golden-value tested against synthetic, non-personal reference charts. `tests/test_calc_regressions.py` is the canonical pattern: synthetic charts only, invariant assertions (e.g. Chart longitudes equal a direct UT swisseph computation for any non-zero timezone). **No personal or family birth data ever enters tests, fixtures, plans, or committed reference files** — synthesize charts or assert invariants instead.
- Any change to a calculation module (`bphs_core/*`) that could shift a numeric output requires a golden/regression test that first failed (per the parent workspace's test-first non-negotiable) and pins the expected value. "It runs" is not sufficient evidence for an accuracy engine.
- Fail-closed determinism governs the electional (muhurat / lagna-shuddhi) pipeline: a limb that cannot be computed (tithi crash, hard-gate failure, eclipse/adhika-maasa resolving to `None`) must degrade to "not recommendable / visibly degraded" — **never** silently to "fine / auspicious". `tests/test_panchanga_fail_closed.py` is the contract; extend it, never weaken it. One-sentence mandate: a missing limb means visibly degraded, never a clean pass.
- **A dependency's wire shape is pinned by a test that drives the REAL callee — a fabricated fixture validates a fiction, and can pin the defect itself as expected.** Measured 2026-08-05: the 30-muhurta limb served an **empty list behind HTTP 200 on every single request**, with `degraded` reporting `False`. `drik.muhurthas()` returns 30 entries shaped `(name, auspicious_flag, (start_hours, end_hours))`; the parser sniffed `isinstance(entry, tuple) and len(entry) >= 2` — which the real 3-tuple satisfies — then read `entry[0]`, the *name*, as a float hour, so `float_hours_to_hhmm` raised `TypeError` on every iteration and a bare `except Exception` wrapped around the whole loop turned it into a log line. The suite could not see it because the test monkeypatched `drik.muhurthas` with `(6.0, 6.8)` 2-tuples the library has never returned, and then **asserted the empty list as the expected result** — encoding the bug as correct behaviour, so a correct implementation would have failed the suite. Five standing rules follow, and they generalise to every `drik.*`/`swe.*` return this engine parses:
  - Every limb that parses a third-party return carries at least one test driving the **unpatched** callee, asserting the **structured** result — how many entries, which names, what boundaries. `assert result != []` passes on a single garbage entry and is not evidence.
  - A broad `except` wraps **only** the foreign call, never the parsing of its result. Use `try/except/else`: the environmental failure mode (sunrise/sunset at extreme latitudes) degrades visibly inside `except`; the parse sits in `else`, where a contract break **raises** instead of being served as silence. An empty field a consumer cannot distinguish from a real answer is worse than a 500 — the 500 is visible and recoverable.
  - Monkeypatching a foreign function is legitimate to simulate **failure**, never to invent a **success** shape. If a test needs a success shape, it must be the shape the library actually produces, pinned by a sibling test that reads the library directly.
  - Parse strictly and reject an unexpected **count** as well as an unexpected shape: positional labelling (`_MUHURTA_NAMES[i]`) silently mislabels every window if the library's entry count ever moves, and `idx % 30` wrapping hides exactly that.
  - **Where a label is assigned by index, pin the dependency's own ORDER — a count check and a shape check are both blind to a reorder.** This is the same defect class as the two planet-id spaces above: positional identity carried across a library boundary. `drik.muhurthas` names its entries from the insertion order of `jhora.const.muhurthas_of_the_day` while deriving the time slots from the index, so discarding `entry[0]` and labelling slot *i* with `_MUHURTA_NAMES[i]` is correct only while that key order holds. Measured 2026-08-05: transposing **two adjacent keys** — the shape a real upstream change takes — served window 1 as "Ahi" where the library called it `mithra` and window 2 as "Mitra" where the library called it `aahi`, with `degraded: False`, every entry still matching the contracted 3-tuple, the count still 30, the windows still tiling the day contiguously, and **all 82 tests then covering this limb green** (`tests/test_muhurat_deep.py` + `tests/test_panchanga_fail_closed.py`). Comparing served labels to `_MUHURTA_NAMES` cannot catch it — that is the constant they were copied from, so the assertion is tautological with respect to ordering. The library's `(name, flag)` sequence is therefore pinned position by position (`tests/test_muhurat_deep.py`, `_MUHURTA_POSITIONAL_SIGNATURE`), together with the label each slot must serve under. **Pin the dependency's own names, not a derived signature.** The auspicious flags are the tempting choice because they carry no transliteration risk, but measured on this table they catch only **11 of the 29** adjacent transpositions (37.9%) and 189 of the 435 total (43.4%) — the flag column takes only **two** values across the 30 positions, so most neighbouring pairs share one, and a transposition of two **same-flag neighbours** is invisible to it — whereas the names, being dict keys, are unique and so move under **every** transposition (29/29 and 435/435). A flags-only pin catches the `aahi`/`mithra` swap above and stays green on `rudra`/`aahi`, which both carry flag 0 and mislabels two windows just as thoroughly. Every count in this paragraph is **computed** from the pinned table by `tests/test_muhurat_deep.py::TestSignatureColumnDiscrimination`, which asserts each one: cite what that test computes, and never re-count the table by hand into prose here. That last clause is itself a correction — this sentence used to gloss the mechanism as a hand-counted run of identical flags, the run length was wrong, and it had been copied into two further places before anyone re-*derived* it instead of re-*reading* it. The flag is kept as a *second*, spelling-independent signature, because it is the only column that moves when a key holds its position while its auspiciousness value changes. The cost of pinning names is a red test on a benign upstream respelling — which lands only inside a deliberate dependency bump this repo already requires to be handled deliberately, and which is the moment the label correspondence should be re-derived anyway. Production keeps discarding `entry[0]` rather than comparing it (`bphs_core/muhurat.py`, comment at the parse loop): comparing there would make a harmless respelling a 500 on every request, and the served path cannot tell a respelling from a reorder without the same pinned table.

## API contract stability

Endpoints are versioned under `/v1/*` (chart, strength, dashas, yogas, transits, special-points, profile, muhurat, muhurat.lagna-shuddhi, muhurat.family-lagna-shuddhi, compat — all POST; plus GET /source, GET /healthz). Response models live in `app/schemas.py` and are the wire contract with the caller.

- A backward-incompatible change to any request or response schema (removed/renamed field, changed type or units, tightened enum) requires a version bump (a new `/vN/` path) — never an in-place mutation of `/v1`. Additive optional fields are fine. Never break `/v1` in place; the caller pins to it.
- `/source` (authenticated) returns `{source_url, commit}`, where `commit` is the cache-invalidation key resolved by `_resolve_version()` (main.py:41-89): `GIT_COMMIT` env (baked at image build, Dockerfile `ARG`/`ENV`) is authoritative; the source-content hash `src-<sha256[:16]>` is the dev fallback; the literal `unknown` is the non-cacheable sentinel. Never substitute a fabricated commit for `unknown` — the caller keys its result cache on this value, and a wrong key serves stale astronomy.

## HTTP service hardening

- Auth fails **closed**. `app/auth.py` refuses to start (`raise RuntimeError` at import time, auth.py:64) when `ENVIRONMENT` is outside `{development, local, test}` and `CALC_SERVICE_TOKEN` is missing, a known placeholder, or shorter than 16 characters. `ENVIRONMENT` defaults to `production` precisely so a missing value is fail-secure (auth.py:20). Rules: (1) never change that default to a permissive value; (2) never add a code path that serves an authenticated endpoint when the token is unset outside dev; (3) token comparison uses `hmac.compare_digest` — never `==` (timing attack surface) (auth.py:111); (4) the app secret travels in its own header, `X-Calc-Service-Token`; `Authorization` is reserved for the platform's OIDC identity token — never merge the two into one header (auth.py:85-94).
- `/healthz` is intentionally unauthenticated (liveness probe, no sensitive body, main.py:603-606) — keep its body limited to a status string plus an `ephe_loaded` boolean; never add sensitive data to it.
- Validate every endpoint at the schema boundary: latitude `ge=-90, le=90`, longitude `ge=-180, le=180`, timezone `ge=-12, le=14`, and every float field carries `allow_inf_nan=False`. Hard rule on the NaN subtlety: `ge`/`le` alone do **not** reject NaN (IEEE-754 comparisons with NaN are always false), so a NaN value passes range checks and flows into `swe.houses()` / `drik.Place()`, producing a finite-but-wrong chart. Every new float input field **must** set `allow_inf_nan=False` (see `app/schemas.py` and the contract in `tests/test_coord_bounds.py`). Also bound expensive-scan inputs — date-range caps (`MAX_*_DAYS`), `step_seconds >= 60`, family members `2..6` — so a single request cannot force an unbounded compute.
- The 422 handler must never regress into a 500: `_validation_exception_handler` sanitizes non-finite floats and exception objects before serializing (main.py:146). Keep validation rejections as well-formed 422s.
- Keep-alive / stale-connection handling is a two-sided contract. Server side: uvicorn runs with `--timeout-keep-alive 75` (Dockerfile CMD) so idle pooled connections aren't closed out from under a client mid-send (which otherwise surfaces as an `httpx.ReadError`) — keep this value at or above any upstream/load-balancer idle timeout. Client-side retry of the residual race is the caller's responsibility, not this repo's. If you change one side of this contract, reason about both.
- CORS `allow_origins` is driven by the `ALLOWED_ORIGINS` env var (main.py:91,111) and is empty by default — this is a server-to-server service. Do not introduce a wildcard `["*"]` origin.

## Async scanning design — the GIL trade-off

The service runs single-threaded under Python's GIL. A wide date-range electional scan (up to `MAX_LAGNA_SHUDDHI_DAYS` days) can occupy a request thread for its full duration, starving concurrent chart requests and risking the caller's connection/proxy timeout. The async submit/poll endpoint (`app/jobs.py`) solves this: it hands back a job id immediately and runs the scan on a small background thread pool, decoupled from the submitting request's lifecycle.

**What it solves:** the connection timeout problem for long-running scans. The HTTP call that submits a scan returns right away; the caller polls for results separately.

**What it does NOT solve:** GIL contention. The background thread pool and the sync `/v1/*` handlers share the single process's GIL. CPU-bound scans and interactive chart requests still contend, degrading latency of concurrent sync handlers while a scan runs. The design's own docstring (`app/jobs.py` lines 1–18) already acknowledges this. The thread pool is deliberately kept small (`max_workers=4`) to bound the contention, and the design ensures submissions and polls (which only touch a lock-protected dict) remain O(1) and never wait on scan compute.

**Why the trade-off is accepted:** (1) it solves a real, reported problem (caller connection timeouts); (2) residual latency degradation is bounded by `max_workers=4` and occurs only during a scan; (3) the caller has a durable synchronous path (`/v1/muhurat`, `/v1/muhurat.lagna-shuddhi`) as the canonical route — the async variant is strictly additive; (4) job state is process-local and does not survive a restart, acceptable because the sync path remains intact; (5) no evidence of a breached latency SLO today.

**If the decision reverses:** should a latency SLO be breached or the caller profile change to many concurrent scans, isolate scan CPU in a subprocess or `multiprocessing.Pool` to eliminate GIL contention. This would require separate infrastructure (subprocess management, IPC, cleanup on restart) — acceptable at that point, but not now.

## Supply-chain & image hygiene

- The shipped Docker image installs from the committed, frozen lockfile: `Dockerfile` copies `pyproject.toml`/`uv.lock` into the build context and runs `uv sync --frozen` (once for third-party deps, once for the project itself), so the deployed dependency set is provably the tested one — there is no floating `pip install -e .` step left. Keep it this way; never reintroduce an unpinned resolve at build time.
- **Every external image is a digest-pinned `FROM`, never a `COPY --from=<registry image>` — and the two halves of that rule are independent.** Both Dockerfiles used to install the build tool with `COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/`, defended by a comment arguing a floating tag was fine for an installer. It was not, for two separate reasons, and fixing either one alone leaves the image floating. (1) `:latest` is re-resolved on **every** build, so two builds of the same commit can install different bytes with nothing recording which shipped — in an image whose every other input is pinned (`.python-version`, `uv.lock` under `uv sync --frozen`, the ephemeris files to sha256). (2) **`COPY --from=<registry image>` is invisible to dependabot**, whose `docker` ecosystem parses `FROM` instructions only — so an image reached that way is never bumped for a disclosed CVE and never reported as outdated *however carefully it is pinned*. Pinning the digest on the `COPY` would therefore have traded a mutable reference for a frozen, unwatched one, which rots quietly instead of loudly. The required shape is `FROM <image>:<version>@sha256:<digest> AS <name>` + `COPY --from=<name>`: the digest makes the build reproducible, the **version tag** makes it maintainable (dependabot compares tags to decide a newer release exists, and a digest-only reference is frozen forever), and the `FROM` makes it visible. Resolve a digest with `docker buildx imagetools inspect <image>:<version>` — take the multi-arch **index** digest, never a per-platform one, and never hand-write a digest. The bare official base (`python:3.11-slim`) is the one exemption from the digest requirement, because its tag is separately asserted against `.python-version` by `ci/tests/test_environment_convergence.py` — a floating tag there is still rejected. - **Run the EXACT command CI runs, not an equivalent — `pytest X` and `python -m pytest X` are not the same command.** `python -m pytest` prepends the CWD to `sys.path`; the bare `pytest` console script does not. `ci/` has no `__init__.py` by design, so `from ci import …` resolves under the first form and raises `ModuleNotFoundError: No module named 'ci'` under the second. The CI-invoked forms are, verbatim: `uv run --frozen pytest tests/ -q`, `uv run --frozen pytest ci/tests/ -q`, `uv run --frozen pytest tests/ --cov --cov-report=term-missing`, and — only for the accuracy job — `uv run --frozen python -m pytest tests/ -q`.
